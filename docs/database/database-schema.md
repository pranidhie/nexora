# NEXORA Procurement Database Schema

## 1. Purpose

This document defines the PostgreSQL database schema for the NEXORA Procurement Management module.

The schema is based on the approved:

- Business processes
- User roles
- User stories
- Business rules
- Functional requirements
- Non-functional requirements
- Procurement ERD

The database design supports the first implementation phase of NEXORA, including:

- User authentication and role-based access
- Supplier management
- Raw material and item catalogue management
- Supplier-item purchasing information
- Purchase requisitions
- Standard purchase orders
- Direct purchase orders
- Approval workflows
- Status history
- Notifications
- Audit history

Goods receipt, inventory, supplier invoicing, three-way matching and accounting integration will be introduced in later phases.

---

# 2. Database Standards

## 2.1 Naming Convention

The database shall use:

- `snake_case` for schemas, tables and columns
- Plural names for tables
- Singular names for entity references
- `_id` suffix for primary and foreign keys
- `_at` suffix for timestamp columns
- `_date` suffix for date-only columns
- `_code` suffix for business codes
- `_status` or `status` for lifecycle values

Examples:

```text
purchase_orders
supplier_contacts
purchase_order_id
created_at
required_delivery_date
supplier_code
```

---

## 2.2 Primary Keys

All main tables shall use:

```text
bigint generated by default as identity
```

Primary keys shall not carry business meaning.

Business identifiers such as Supplier Code, Item Code, Requisition Number and Purchase Order Number shall use separate unique columns.

---

## 2.3 Date and Time

The database shall use:

```text
timestamptz
```

for system timestamps such as:

- `created_at`
- `updated_at`
- `submitted_at`
- `approved_at`
- `sent_at`

The database shall use:

```text
date
```

for business dates such as:

- Required Date
- Order Date
- Required Delivery Date
- Price Effective Date

---

## 2.4 Monetary Values

Monetary amounts shall use:

```text
numeric(18,2)
```

Quantities and conversion factors shall use:

```text
numeric(18,4)
```

Floating-point data types shall not be used for financial calculations.

---

## 2.5 Status Values

Status fields shall use uppercase values.

Examples:

```text
ACTIVE
INACTIVE
DRAFT
SUBMITTED
PENDING_APPROVAL
APPROVED
REJECTED
CANCELLED
```

PostgreSQL `CHECK` constraints shall initially be used for controlled values.

Native PostgreSQL enums may be considered later if the lifecycle values become stable.

---

## 2.6 Audit Columns

Business tables should include:

```text
created_at
created_by
updated_at
updated_by
```

where appropriate.

Historical transaction records shall not be permanently deleted.

# 3. Security Tables

## 3.1 `users`

### Purpose

Stores registered NEXORA users and account information required for authentication.

| Column | PostgreSQL Type | Required | Key | Default | Description |
|---|---|---:|---|---|---|
| `user_id` | `bigint` | Yes | PK | Identity | Unique user identifier |
| `first_name` | `varchar(100)` | Yes |  |  | User's first name |
| `last_name` | `varchar(100)` | Yes |  |  | User's last name |
| `email` | `varchar(255)` | Yes | UK |  | Unique login email |
| `password_hash` | `varchar(255)` | Yes |  |  | Securely hashed password |
| `status` | `varchar(20)` | Yes |  | `ACTIVE` | Account status |
| `last_login_at` | `timestamptz` | No |  |  | Most recent successful login |
| `created_at` | `timestamptz` | Yes |  | `current_timestamp` | Creation timestamp |
| `updated_at` | `timestamptz` | Yes |  | `current_timestamp` | Last update timestamp |

### Constraints

- `email` must be unique.
- `email` shall be stored in a normalised lowercase format.
- `status` must be one of:
  - `ACTIVE`
  - `INACTIVE`
  - `LOCKED`
- Passwords must never be stored in plain text.

### Indexes

- Unique index on `email`
- Index on `status`
- Index on `last_name`, `first_name`

---

## 3.2 `roles`

### Purpose

Stores system roles used by role-based access control.

| Column | PostgreSQL Type | Required | Key | Default | Description |
|---|---|---:|---|---|---|
| `role_id` | `bigint` | Yes | PK | Identity | Unique role identifier |
| `role_code` | `varchar(50)` | Yes | UK |  | Stable system role code |
| `role_name` | `varchar(100)` | Yes | UK |  | Human-readable role name |
| `description` | `text` | No |  |  | Description of responsibilities |
| `active` | `boolean` | Yes |  | `true` | Whether the role can be assigned |
| `created_at` | `timestamptz` | Yes |  | `current_timestamp` | Creation timestamp |
| `updated_at` | `timestamptz` | Yes |  | `current_timestamp` | Last update timestamp |

### Initial Role Codes

```text
REQUESTER
PROCUREMENT_OFFICER
NOMINATED_APPROVER
PROCUREMENT_MANAGER
SYSTEM_ADMINISTRATOR
```

Future roles may include:

```text
WAREHOUSE_OFFICER
QUALITY_OFFICER
ACCOUNTS_PAYABLE_OFFICER
AUDITOR
```

### Constraints

- `role_code` must be unique.
- `role_name` must be unique.
- Inactive roles cannot be newly assigned.

### Indexes

- Unique index on `role_code`
- Unique index on `role_name`
- Index on `active`

---

## 3.3 `user_roles`

### Purpose

Creates a many-to-many relationship between users and roles.

A user may have more than one role.

| Column | PostgreSQL Type | Required | Key | Default | Description |
|---|---|---:|---|---|---|
| `user_role_id` | `bigint` | Yes | PK | Identity | Unique assignment identifier |
| `user_id` | `bigint` | Yes | FK |  | References `users.user_id` |
| `role_id` | `bigint` | Yes | FK |  | References `roles.role_id` |
| `assigned_at` | `timestamptz` | Yes |  | `current_timestamp` | Assignment timestamp |
| `assigned_by` | `bigint` | No | FK |  | User who assigned the role |
| `active` | `boolean` | Yes |  | `true` | Whether the assignment is active |

### Foreign Keys

- `user_id` → `users.user_id`
- `role_id` → `roles.role_id`
- `assigned_by` → `users.user_id`

### Constraints

- A user cannot have the same active role assigned more than once.
- Only active roles may be assigned.
- Deactivating a role assignment must preserve the historical record.

### Indexes

- Unique index on `user_id`, `role_id` where `active = true`
- Index on `user_id`
- Index on `role_id`
- Index on `active`

---

# 4. Supplier Tables

## 4.1 `suppliers`

### Purpose

Stores suppliers approved or considered for procurement transactions.

| Column | PostgreSQL Type | Required | Key | Default | Description |
|---|---|---:|---|---|---|
| `supplier_id` | `bigint` | Yes | PK | Identity | Unique supplier identifier |
| `supplier_code` | `varchar(30)` | Yes | UK |  | Unique business supplier code |
| `supplier_name` | `varchar(200)` | Yes |  |  | Registered or trading name |
| `email` | `varchar(255)` | No |  |  | General supplier email |
| `phone` | `varchar(50)` | No |  |  | General phone number |
| `address_line_1` | `varchar(200)` | No |  |  | Primary address line |
| `address_line_2` | `varchar(200)` | No |  |  | Secondary address line |
| `city` | `varchar(100)` | No |  |  | City or suburb |
| `state_region` | `varchar(100)` | No |  | State or region |
| `postal_code` | `varchar(20)` | No |  | Postal code |
| `country_code` | `varchar(3)` | No |  | Country code |
| `tax_registration_number` | `varchar(50)` | No |  | ABN or equivalent |
| `payment_terms` | `varchar(100)` | No |  | Default payment terms |
| `status` | `varchar(20)` | Yes |  | `ACTIVE` | Supplier lifecycle status |
| `notes` | `text` | No |  |  | General notes |
| `created_at` | `timestamptz` | Yes |  | `current_timestamp` | Creation timestamp |
| `created_by` | `bigint` | Yes | FK |  | User who created the supplier |
| `updated_at` | `timestamptz` | Yes |  | `current_timestamp` | Last update timestamp |
| `updated_by` | `bigint` | Yes | FK |  | User who last updated it |

### Foreign Keys

- `created_by` → `users.user_id`
- `updated_by` → `users.user_id`

### Constraints

- `supplier_code` must be unique.
- `supplier_name` is mandatory.
- `status` must be one of:
  - `ACTIVE`
  - `INACTIVE`
  - `ON_HOLD`
- Email must use a valid format when provided.
- Suppliers with procurement history must be deactivated rather than deleted.

### Indexes

- Unique index on `supplier_code`
- Index on `supplier_name`
- Index on `status`
- Index on `tax_registration_number`

---

## 4.2 `supplier_contacts`

### Purpose

Stores one or more contacts for each supplier.

| Column | PostgreSQL Type | Required | Key | Default | Description |
|---|---|---:|---|---|---|
| `supplier_contact_id` | `bigint` | Yes | PK | Identity | Unique supplier contact identifier |
| `supplier_id` | `bigint` | Yes | FK |  | Parent supplier |
| `contact_name` | `varchar(150)` | Yes |  | Contact person's name |
| `job_title` | `varchar(100)` | No |  | Position or job title |
| `email` | `varchar(255)` | No |  | Contact email |
| `phone` | `varchar(50)` | No |  | Contact phone |
| `primary_contact` | `boolean` | Yes |  | `false` | Whether this is the primary contact |
| `active` | `boolean` | Yes |  | `true` | Whether this contact can be selected |
| `created_at` | `timestamptz` | Yes |  | `current_timestamp` | Creation timestamp |
| `created_by` | `bigint` | Yes | FK |  | User who created the contact |
| `updated_at` | `timestamptz` | Yes |  | `current_timestamp` | Last update timestamp |
| `updated_by` | `bigint` | Yes | FK |  | User who updated the contact |

### Foreign Keys

- `supplier_id` → `suppliers.supplier_id`
- `created_by` → `users.user_id`
- `updated_by` → `users.user_id`

### Constraints

- Contact email must use a valid format when provided.
- A supplier may have multiple contacts.
- A supplier should have no more than one active primary contact.
- Contacts used in previous transactions must not be permanently deleted.

### Indexes

- Index on `supplier_id`
- Index on `email`
- Index on `active`
- Partial unique index on `supplier_id` where:
  - `primary_contact = true`
  - `active = true`

## 5.3 `catalogue_items`

### Purpose

Stores raw materials, ingredients, packaging, services and other purchasable items.

| Column | PostgreSQL Type | Required | Key | Default | Description |
|---|---|---:|---|---|---|
| `catalogue_item_id` | `bigint` | Yes | PK | Identity | Unique catalogue item identifier |
| `item_code` | `varchar(50)` | Yes | UK |  | Unique business item code |
| `item_name` | `varchar(200)` | Yes |  |  | Item name |
| `item_type` | `varchar(40)` | Yes |  |  | Item classification |
| `category_id` | `bigint` | Yes | FK |  | Item category |
| `purchase_uom_id` | `bigint` | Yes | FK |  | Default purchase unit |
| `stock_uom_id` | `bigint` | No | FK |  | Default stock unit |
| `conversion_factor` | `numeric(18,4)` | No |  |  | Purchase-to-stock conversion |
| `shelf_life_days` | `integer` | No |  |  | Expected shelf life |
| `storage_condition` | `varchar(200)` | No |  |  | Required storage condition |
| `batch_tracking_required` | `boolean` | Yes |  | `false` | Whether batch capture is required |
| `expiry_tracking_required` | `boolean` | Yes |  | `false` | Whether expiry capture is required |
| `allergen_information` | `text` | No |  |  | Allergen details |
| `country_of_origin` | `varchar(100)` | No |  |  | Country of origin |
| `status` | `varchar(20)` | Yes |  | `ACTIVE` | Catalogue item status |
| `created_at` | `timestamptz` | Yes |  | `current_timestamp` | Creation timestamp |
| `created_by` | `bigint` | Yes | FK |  | User who created the item |
| `updated_at` | `timestamptz` | Yes |  | `current_timestamp` | Last update timestamp |
| `updated_by` | `bigint` | Yes | FK |  | User who updated the item |

### Foreign Keys

- `category_id` → `item_categories.category_id`
- `purchase_uom_id` → `units_of_measure.uom_id`
- `stock_uom_id` → `units_of_measure.uom_id`
- `created_by` → `users.user_id`
- `updated_by` → `users.user_id`

### Allowed Item Types

```text
RAW_MATERIAL
INGREDIENT
PACKAGING_MATERIAL
CLEANING_MATERIAL
MAINTENANCE_ITEM
NON_STOCK_ITEM
SERVICE
```

### Constraints

- `item_code` must be unique.
- `item_name` is mandatory.
- `status` must be `ACTIVE` or `INACTIVE`.
- `conversion_factor` must be greater than zero when purchase and stock units differ.
- `stock_uom_id` may be null for services and authorised non-stock items.
- Only active items may be added to new procurement documents.

### Indexes

- Unique index on `item_code`
- Index on `item_name`
- Index on `item_type`
- Index on `category_id`
- Index on `status`
- Index on `batch_tracking_required`
- Index on `expiry_tracking_required`

## 5.4 `supplier_items`

### Purpose

Stores supplier-specific purchasing information for catalogue items.

| Column | PostgreSQL Type | Required | Key | Default | Description |
|---|---|---:|---|---|---|
| `supplier_item_id` | `bigint` | Yes | PK | Identity | Unique supplier-item record |
| `supplier_id` | `bigint` | Yes | FK |  | Supplier |
| `catalogue_item_id` | `bigint` | Yes | FK |  | Catalogue item |
| `supplier_item_code` | `varchar(100)` | No |  |  | Supplier's own item code |
| `purchase_uom_id` | `bigint` | Yes | FK |  | Supplier purchase unit |
| `unit_price` | `numeric(18,2)` | Yes |  |  | Current supplier price |
| `currency_code` | `varchar(3)` | Yes |  | `AUD` | Currency |
| `minimum_order_quantity` | `numeric(18,4)` | No |  |  | Minimum purchasable quantity |
| `lead_time_days` | `integer` | No |  |  | Expected lead time |
| `preferred_supplier` | `boolean` | Yes |  | `false` | Whether supplier is preferred |
| `effective_from` | `date` | Yes |  | `current_date` | Price validity start |
| `effective_to` | `date` | No |  |  | Price validity end |
| `active` | `boolean` | Yes |  | `true` | Whether the relationship is active |
| `created_at` | `timestamptz` | Yes |  | `current_timestamp` | Creation timestamp |
| `created_by` | `bigint` | Yes | FK |  | Creator |
| `updated_at` | `timestamptz` | Yes |  | `current_timestamp` | Last update timestamp |
| `updated_by` | `bigint` | Yes | FK |  | Last updater |

### Foreign Keys

- `supplier_id` → `suppliers.supplier_id`
- `catalogue_item_id` → `catalogue_items.catalogue_item_id`
- `purchase_uom_id` → `units_of_measure.uom_id`
- `created_by` → `users.user_id`
- `updated_by` → `users.user_id`

### Constraints

- `unit_price` must be zero or greater.
- `minimum_order_quantity` must be greater than zero when provided.
- `lead_time_days` must be zero or greater when provided.
- `effective_to` must not be earlier than `effective_from`.
- Only active suppliers and active items may be linked for new use.
- Duplicate active supplier-item-price periods must be prevented.
- An item should have no more than one active preferred supplier at a time.

### Indexes

- Index on `supplier_id`
- Index on `catalogue_item_id`
- Index on `supplier_item_code`
- Index on `active`
- Index on `preferred_supplier`
- Composite index on:
  - `supplier_id`
  - `catalogue_item_id`
  - `effective_from`
